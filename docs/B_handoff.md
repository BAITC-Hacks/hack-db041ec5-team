Для C: graph.json использует строковые id/source/target, CSV — int64.

Ветка Kostya включает коммит Artyom df14809 и часть B. Модули A не изменены.

```python
from run import analyze, run_pipeline
F, R, P, C, G = analyze(nodes, edges, transactions, cfg)
report = run_pipeline('data', 'output', 'config.yaml')
```

analyze — ядро без файловых побочных эффектов. run_pipeline читает parquet,
пишет отчёт качества, обязательные и дополнительные выгрузки, возвращает отчёт.
Все исключения ядра пробрасываются; отчёт получает status=failed.

Для C: nodes_roles.csv, clusters.csv, top_nodes.csv имеют точные схемы из плана.
graph.json формирует функция A build_graph_json с ролями/приоритетами B.
В node_features.csv сохранены role (строка), role_score, secondary_role,
base_role, n_role_nb, rule_fired, score_* и компоненты priority_money,
priority_convergence, priority_position, priority_role. Последние имеют префикс,
чтобы числовой компонент role не конфликтовал со строковой ролью.
contribution_* — взвешенные вклады с учётом seed_discount; их сумма даёт
priority_score. freq_top20 — доля вариантов весов, NaN при runs=0.
При изменении stability.top_k поле сохраняет имя freq_top20 ради контракта;
фактический размер топа указан в why и run_report.json.
median_out — медиана исходящих транзакций; max_payers_date — самый ранний день
максимального числа плательщиков в формате ДД.ММ.

Кластеризация в analyze выполняется на временных позиционных метках и затем
возвращает исходные gid: это убирает зависимость равных кластеров A от строкового
представления gid. Прямой вызов A.cluster по исходным gid может иначе пронумеровать
равные кластеры. Части C следует использовать готовую cluster_id из общего пайплайна.
